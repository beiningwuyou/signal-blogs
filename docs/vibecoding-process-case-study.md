# 从原型延续到产品偏移：Signal Desk 的 Vibe Coding 开发流程案例研究

**报告日期：**2026 年 9 月 9 日  
**研究对象：**Signal Desk 从高保真原型转换、继续开发到交付争议的协作过程  
**报告性质：**基于本次对话与本地工程材料的单案例复盘，不是关于大语言模型能力的对照实验  
**状态：**问题分析与改进方案；不代表用户已批准重建，也不代表改进措施已经全部实施

## 摘要

本案例研究一个具体问题：用户已提供完整产品原型，并希望在已有成果上继续开发，为什么后续实施仍产生了较多工作，而交付效果未达到用户预期？

通过对本次对话、当前路由代码、项目上下文与开发验收记录的交叉核对，可以确认：开发确实补充了真实 RSS 获取、事件聚合、持久化和异常恢复等能力，但同时新增了一套以“精选／全部事件／收藏”为中心的工作台，将用户原先强调的“每日早报／正在关注”放入保留的原型区域。工程继续使用既有技术栈，并非从零重写全部系统；发生实质偏移的是产品入口、信息架构和功能承载页面。

本报告认为，最直接的问题是 Agent 在需求与原型存在冲突时，自行决定了产品结构，并将技术功能的完成程度作为整体交付完成的主要依据。多份文档之间的职责重叠、既有成果的保留边界不清，以及缺少早期产品对照验收，扩大了这种偏移。现有证据不能证明“上下文过长导致遗忘”是模型内部的确定原因，也不足以计算重复开发造成的精确时间损失。

解决方向是建立可追溯的产品基线、明确文件分工、以现有代码为起点划定本轮改动，并把产品一致性纳入验收。对于当前项目，先比较修复与重建方案，再决定实施路径；即使重新建立前端，也应保留并评估已验证后端的复用价值。

## 一、问题描述

### 1.1 用户预期与实际交付

用户最初提供了 `DESIGN.md`、14 个高保真页面及静态 HTML、交互脚本，并要求按既定设计系统封装布局、侧边栏、卡片与研读抽屉，优先实现“每日早报”和“正在关注”。要求不仅涉及颜色，也包括中文文案、交互状态和信息层级。[E1]

后续用户要求结合 `agent.md` 与产品原型继续全栈开发。这扩大了功能实现范围，但没有明确提出用另一套导航替换原先的产品呈现。用户事后进一步明确，其预期是延续已有 MVP，而不是再次生成另一套主界面。[E1]

实际代码中，默认路由进入 `/events`，`/all` 与 `/bookmarks` 由新的 `LiveLayout` 和 `Workbench` 承载；原来的 `/daily`、`/following` 则继续使用另一套布局与页面。项目文档也明确把原页面称为演示页面，并将新工作台称为正式业务入口。[E2][E3]

| 观察维度 | 用户预期 | 实际结果 | 问题性质 |
| --- | --- | --- | --- |
| 开发起点 | 在已有原型与可运行成果上补齐功能 | 保留旧页面，同时新增正式工作台 | 成果延续方式不一致 |
| 核心页面 | 每日早报、正在关注优先 | 精选、全部事件、收藏成为主入口 | 信息架构发生变化 |
| 原型作用 | 后续开发的界面与交互依据 | 主要保留暖纸视觉，核心结构另按文本要求实现 | 原型约束被缩小 |
| 时间投入 | 复用成果，尽快形成可用产品 | 增加工作台、后端和多轮验证 | 用户感知成本上升 |
| 完成判断 | 既符合原型，又能完成实际任务 | 技术测试通过后宣布核心版本完成 | 验收口径不一致 |

### 1.2 本报告对“重新开发”和“MVP”的界定

“重新开发”在本案中不能理解为所有代码被删除重写。当前工程沿用了 React、Vite、Node、SQLite 和 Electron，也保留了此前页面及个人记录。更准确的表述是：**在已有工程内部重新组织了产品主界面，并为新增工作台接入真实业务能力。**[E2][E3]

用户将前期成果称为 MVP，反映出其已经认可了一定程度的产品形态和交互。工程材料则表明，部分前期内容仍依赖演示数据，真实抓取等能力是在后续补入的。[E3][E4] 两种描述并不必然矛盾：前期成果可以是可运行、可体验的前端版本，同时尚未完成全部真实业务链路。正确做法应是明确哪些功能还缺失，而不是因数据尚未真实接通就重新定义整个产品。

### 1.3 影响与证据边界

本次已观察到的影响包括用户对耗时和效果的不满、对开发路径的信任下降，以及重新评估开发流程和是否重建的需要。[E1] 工程中两套页面体系并存，也增加了后续确定主入口与复用边界的工作。[E2]

但本报告不把全部后端开发和测试视为浪费。这些工作中包含真实功能和必要的数据保护措施。现有材料没有完整、可独立核验的逐阶段工时记录、费用分解或替代实现，因此不能声称某个方案必然节省多少时间，也不能把主观“不好看”换算成未经测量的设计质量分数。

## 二、如何进行的：过程还原与分析方法

### 2.1 用户描述的开发流程

用户原有流程可归纳为：idea 深化为 PRD，经 Stitch 生成并导出原型，再选择技术栈、初始化本地工程，生成 README 与 `agent.md`，最后由 Codex 开始全栈开发并在界面上迭代。[E1]

这条流程已经包含需求、设计、工程和迭代环节。薄弱之处在于各环节之间的交接：原型已经确认了哪些产品决定，文档总结是否改变了这些决定，以及“继续开发”究竟允许修改哪些部分，没有形成一致的执行边界。关于 Stitch 的具体生成和人工调整过程，本次对话没有完整操作记录，本报告只采用用户对流程的描述，不推断其内部细节。

### 2.2 本案的主要阶段

| 阶段 | 输入或动作 | 结果及其意义 |
| --- | --- | --- |
| 原型交接 | 用户提供设计规范、14 页原型，指定核心页面和组件 | 已有明确的页面与视觉约束 |
| 前端实现 | 转为 React 组件，加入路由及本地交互 | 建立了后续应优先复用的页面与组件 |
| 扩展开发 | 用户要求结合 `agent.md` 和原型完成项目 | 需要核对需求差异，并明确真实业务缺口 |
| 路径选择 | Agent 采用“业务以 agent.md 为准、视觉遵循原型”的分法 | 将包含交互与信息架构的原型，主要解释为视觉参考 |
| 全栈实施 | 增加真实抓取、数据模型、研究任务和新工作台 | 业务能力增加，产品主入口也随之变化 |
| 技术验收 | 运行构建、接口、存储、浏览器与 Electron 检查 | 提供实现可运行的证据，但未证明用户认可产品变化 |
| 交付争议 | 用户质疑耗时与效果，讨论上下文和流程 | 暴露出产品一致性与开发者完成判断之间的差距 |

其中最关键的转折是第四阶段。开发方案已经写明默认精选，并将既有原型独立保留为演示入口。[E5] 因此，本案不能仅描述为开发途中偶然忘记要求；结构偏移至少在实施方案阶段就已出现，之后被持续落实到了代码和验收清单中。

### 2.3 研究方法及局限

本报告采用过程还原与材料交叉核对：用用户请求确定预期，用当前代码核实实际入口，用开发文档与验收记录解释实施路径。事实、当事方评价、分析推断和建议分别表述，避免将推断写成实测结果。

需要注意，开发方案和验收记录主要由同一 Agent 生成，不能作为独立的产品验收意见。它们能证明当时记录了什么、围绕什么目标执行，不能证明目标本身已经获得用户认可。本次报告编写未重新运行应用测试；“9 组测试通过”等描述引用的是已有开发记录。[E4] 当前文件也不能完整还原每个历史版本，因此不进行逐次代码变更的精确成本归因。

## 三、问题究因

### 3.1 直接原因：把继续实现误解为可以重新定义产品结构

Agent 获得了补齐功能的授权，却进一步自行决定了主导航、默认入口和原页面的产品地位。功能实现范围与产品设计决策范围被混在一起。“根据 PRD 开发”被解释为足以覆盖此前已经确定的界面结构，而没有先处理两者的具体差异。

这属于执行与判断失误。即使用户没有额外写出“禁止重建”，已有页面、原型约束和“继续”的上下文仍应促使 Agent 优先采用增量方式。补充规则可以降低复发风险，但不能把本次责任归结为用户提示词不够详细。

### 3.2 促成因素：原型与文本需求之间缺少冲突处理机制

本案中，文本描述强调“精选／全部事件／收藏”，原始任务强调“每日早报／正在关注”；视觉描述也存在差异。[E1][E3] Agent 保留了暖纸色系，却采用了另一套导航。这说明其并非完全忽略原型，而是自行缩小了原型的约束范围。

实际上，页面结构、信息优先级、导航与操作入口既属于界面设计，也属于产品行为。简单规定“PRD 管功能、原型管视觉”，不足以处理这些交叉区域。应逐项明确冲突和影响，再由用户决定涉及产品方向的取舍。

### 3.3 促成因素：重复转述使需求来源与状态变得模糊

用户流程中存在 `PRD + 原型 → README → agent.md → 开发` 的连续转述。当前 `agent.md` 同时包含需求、工程现状、技术栈、数据模型和运行规则，并被规定为开发上下文的主要入口。[E3]

这种集中方式并非必然错误，但如果不区分“用户要求”“Agent 建议”“当前实现”和“已验收决定”，就容易把总结中的解释误当作原始要求。实现完成后再把同一解释写回上下文，后续开发便可能把它当作既定事实。

本案中可观察到的链条是：Agent 作出取舍、据此实现新工作台，再将新工作台写入当前实现与验收记录。该链条存在固化未经用户确认的产品选择的风险；但无法据此证明每次文档转述都发生了信息丢失。

### 3.4 促成因素：实施计划没有优先回答“哪些已经做好”

计划覆盖了数据库、抓取、工作台、研究和验证，却没有首先建立“现有页面—缺失能力—可复用代码”的对应关系。[E5] 于是，工作围绕新设定的完整目标展开，而没有优先完成“把真实数据接回原有核心页面”这一更贴近用户意图的路径。

真实 RSS、笔记持久化和失败处理有必要性。问题在于它们被接入新工作台，并与额外界面建设一起推进，而不是先对已有页面完成一条最短的用户流程。不能把该问题简化为“以后少做测试”或“后端越简单越好”。

### 3.5 促成因素：技术验证覆盖了实现，却没有充分覆盖产品目标

已有记录表明，开发确实进行过浏览器操作和尺寸检查，并非完全没有 UI 验证。[E4] 但这些验证主要判断新实现是否可操作、是否溢出、能否保存与恢复，没有在产品结构改变前获得用户对原型偏差的确认。

当实施目标已经偏移，围绕该目标制定的测试仍然可以全部通过。清单完成、构建通过和数据库正确，并不能单独推出“用户要的产品已经完成”。本案的问题是验证对象和验收口径不一致，而不是自动测试本身无价值。

### 3.6 关于“上下文漂移”的判断

在本报告中，“上下文漂移”指开发行动逐渐偏离已确认目标或边界的可观察现象，不等同于模型发生了可测量的记忆故障。

本案确实支持对上下文进行分层和约束管理，但不足以证明上下文窗口长度、摘要压缩、模型注意力分配中的某个因素导致了偏移。更有直接证据的解释是：冲突未被明确解决，Agent 自行作出产品选择，后续文档与验收继续沿用该选择。改善流程应先处理这些可观察、可控制的环节。

## 四、反思

### 4.1 对 Agent 执行责任的反思

原型已经明确到页面、文案与交互时，Agent 应把主要任务从探索产品转向实现既定产品。可以自主处理代码拆分、接口组织等常规细节，但不能因为某种结构更便于实现，就自行改变用户进入和使用产品的方式。

用户指出偏移后，Agent 又较快支持了“重新开发”。这一建议也缺乏充分的方案比较：当时尚未完成修复原页面、新建前端复用后端、完整重建三种方案的具体成本与风险分析。合理回应应是确认用户倾向，同时说明需要哪些证据来决定重建范围，而不是把重建当作已经验证的最优方案。[E1]

### 4.2 对省时方式的反思

省时的关键不是减少必要的持久化、防错与测试，而是避免围绕未确认的产品结构投入大量实现工作。更合适的顺序是先核对已有能力和用户可见的关键差异，再实现一条完整流程，并尽早展示其结果。

静态 HTML 不一定适合直接作为最终应用代码，但其中的布局、文案、状态和信息层级仍是可以继承的成果。组件化是实现形式的转换，不自动意味着获得重新设计的授权。同样，前端已可运行并不意味着真实业务已全部接通，开发者应准确说明缺口，而不是模糊使用“MVP 完成”。

### 4.3 对文档与上下文的反思

更多文档不一定带来更稳定的执行。同一个决定如果被多份文档重复描述，维护负担和解释空间也会增加。上下文管理应强调来源清楚、职责明确、状态可追踪，而不是持续扩写一个包含所有内容的文件。

也不需要每轮都让用户重新讲产品。稳定基线应持续生效；每轮只补充当前任务与新决定。新对话或阶段交接时，应从基线和工程事实恢复，而不是靠再次自由总结全部历史来重新形成产品理解。

### 4.4 对验收与完成表述的反思

应区分三个状态：功能已实现、技术检查已通过、产品已验收。前两者可以由 Agent 提供代码与测试证据，第三者需要对照约定的产品标准；涉及此前未确认的重大变化时，还需要用户作出产品判断。

当系统剪贴板读回等验证未完成时，应保留其具体限制；不能让全勾选清单覆盖局部未完成状态。交付描述同样应避免把“核心版本完成”扩展为对所有产品要求和体验的承诺。

## 五、解决措施

### 5.1 当前项目先止住范围变化，再选择修复或重建

本报告不启动重建、不修改现有业务代码。针对用户已经表达的重开倾向，建议先完成一份简短的工程对照，保留现有代码、原型与用户数据，然后比较以下路径。

| 路径 | 适用条件 | 决定前需要核实 |
| --- | --- | --- |
| 继续修改现有工程 | 原页面可复用，真实数据能以有限改动接入 | 原组件与数据接口的耦合、入口调整范围 |
| 重建前端，复用后端 | 产品呈现需要重新整理，但服务能力仍符合需求 | 后端契约是否适合原页面，迁移与维护成本 |
| 完整重建 | 现有技术栈、核心模型或工程约束与新基线存在根本冲突 | 具体不可复用原因、数据保留方案及替代方案 |

用户可以为了重新验证流程而选择新工程，这属于合理目标；但“新目录”不应自动等于“所有代码从零生成”。只有在明确比较后，才能判断哪些成果应复用、哪些应隔离、哪些确实需要重写。未经用户明确选择，不改变当前唯一开发入口。

### 5.2 建立产品基线和冲突清单

开始实施前，用一页内容固定首版核心页面、主导航、默认入口、关键操作、原型版本、本轮范围与不做事项。直接引用原型和 PRD，不再次扩写一份完整需求。

遇到矛盾时记录“原始要求、原型表现、现有实现、建议处理、影响范围”。普通实现差异由 Agent 自主处理；会改变导航、核心布局、交互语义或首版范围的冲突，由用户决定。等待决定期间继续开展不受影响的工作，避免把冲突管理变成逐步审批。

### 5.3 简化文档分工

| 载体 | 唯一职责 | 应避免的重复 |
| --- | --- | --- |
| `PRD.md` | 用户问题、功能范围与业务验收条件 | 不复制源码目录和安装命令 |
| `DESIGN.md` 与指定原型 | 视觉、文案、布局、交互状态和页面关系 | 不在总结中悄悄改写产品结构 |
| `AGENTS.md` | 权威材料入口、执行边界、复用与验证规则 | 不另写一份完整 PRD |
| `README.md` | 经实际验证的启动、配置和使用方式 | 不作为生成需求的中间文件 |
| 开发清单／工程上下文 | 当前实现、待办、限制与本轮改动 | 不将 Agent 建议写成已批准需求 |

本项目已有 `AGENTS.md → agent.md` 结构，可以暂时保留；文件名称不是根因。若以后调整职责，应与用户确认后的流程一起修改，不在本次报告任务中重新组织工程文档。

### 5.4 使用三层上下文，而不是堆叠全部历史

第一层是稳定的产品基线，包括目标、首版范围和已认可原型；第二层是随代码更新的工程事实，包括唯一目录、实际入口和已实现能力；第三层是本轮任务，包括允许改动、验收条件和待解决冲突。

每轮开始，Agent 简要说明“已有能力、缺失能力、本轮改动”，并核实关键文件。后续“继续”继承基线和既有授权，不触发重新选型、重新生成项目或重新规划产品。交接摘要必须保留未解决问题、用户已作出的决定和测试的局限，不能只保留成功结果。

### 5.5 调整开发顺序与验收节点

建议将流程收敛为：明确 idea 与运行约束 → 编写限定范围的 PRD → 确认 Stitch 原型 → 核对需求、原型和已有代码 → 初始化一次工程及协作规则 → 按用户流程实现 → 在同一成果上迭代。

如果前端原型尚未转成可运行页面，先验收一条核心路径的视觉与交互；如果已经有可运行 MVP，则跳过重复初始化和全页面重做，直接核对缺失能力。无需为了等待全部页面完成，延迟所有前后端集成。

以本项目为例，可以先接通“添加信源 → 获取内容 → 在正在关注中显示 → 研读 → 收藏或保存笔记 → 刷新后回看”，保持原界面，验证数据、交互和持久化，再扩展其他流程。必要的安全和数据完整性要求从相关功能开始就应执行。

### 5.6 将措施落实为可检查的规则

| 措施 | 主要执行者 | 触发时机 | 验收依据 |
| --- | --- | --- | --- |
| 核实唯一工程与入口 | Agent | 开始开发或切换上下文时 | 明确当前目录、启动方式与实际页面 |
| 提交已有能力与缺口对照 | Agent | 新阶段开始前 | 每项开发都能对应已有组件或明确缺口 |
| 固定产品结构 | 用户决定，Agent记录并遵守 | 原型确认及重大变更时 | 导航、默认入口、核心布局与确认版本一致 |
| 显式处理需求冲突 | Agent识别，用户决定产品取舍 | 发现冲突时 | 冲突项有来源、影响和处理状态 |
| 默认增量复用 | Agent | 每次实现 | 新增或替换代码有具体必要性说明 |
| 分开技术与产品验收 | Agent提供证据，用户确认关键产品结果 | 核心流程完成时 | 页面对照、操作结果、测试及未验收项分别记录 |
| 保留工作成果与数据 | Agent | 重建、迁移或切换入口前 | 原件可恢复，数据去向明确，不覆盖未核实内容 |

建议后续记录未经确认的产品结构变更、首次页面验收的差异项、因方向偏移产生的返工任务，以及带有明确验收证据的核心流程数量。这些是未来评估流程是否改善的观察指标，本案尚没有可用于前后比较的统计基线。

### 5.7 可直接复用的开发约束

> 在指定唯一工程中继续开发。先检查现有实现，列出已有能力、缺失能力和本轮改动。默认复用现有页面、组件、技术栈与已验证服务，不新增另一套产品入口。已认可的原型同时约束布局、文案、导航、信息层级和交互状态。PRD 与原型冲突时明确指出，不自行改变产品结构；继续完成不受影响的工作。按完整用户流程接通前后端，以原型对照、实际操作和必要测试共同验收。区分已实现、已验证与用户已验收；未经明确要求不加入后续功能，不提交或发布代码，不执行破坏性迁移。

措施的作用是让偏移能够更早被发现和纠正，不能保证模型永不出错。对本案而言，首要改进不是重写更长的提示词，而是让后续实施始终能够回答：这一改动对应哪项已确认要求，继承了哪些既有成果，是否改变了用户已经确定的产品。
