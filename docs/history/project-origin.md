# Signal Desk 项目定义

## 目标与依据

依据用户提供的《Signal_Desk_产品原型_PRD_V0.2.md》（2026-09-08）及已确认技术栈，建立个人本地信息台。本文维护实施范围与技术决策，详细产品交互以原 PRD 为准。原 PRD 保留在用户文档库，不复制维护第二份。

主流程：配置信源 → 手动获取 → 浏览和筛选事件 → 查看原文 → 收藏或记录判断。

当前阶段已完成基础工程与核心前端原型组件化：每日早报、正在关注、研读抽屉、个人记录与信源配置。新闻正文仍为明确标注的原型数据；尚未接通 RSS 抓取、真实事件聚合与模型研究。

## 范围

### Must

- RSS 信源配置、测试、启停和手动获取，失败保留已有内容。
- 文章去重与事件聚合；精选、全部事件、搜索及分类；具体原文链接可回溯。
- 稳定事件 ID；收藏与最多 500 字个人判断本地保存。
- 选定频道手动研究，展示真实进度与失败状态，结果入库后显示完成。
- 清楚区分事实、来源观点、模型推断、元数据分析与演示数据。

### Later

- 日报、周报、定时获取及复杂分析。
- 正式数据库迁移、备份方案在业务持久化阶段确定；安装包与分发流程在桌面发布阶段补充。

### Not Now

- 多用户账号、付费、权限系统、营销页、社交和对外推送。
- 云数据库、Redis、独立队列服务或额外后端语言。

## 技术与复用

- 前端：Vite + React + React Router + Tailwind CSS 3；本地服务：Node.js 原生 HTTP。
- 数据：SQLite，通过 `src/server/db.js` 集中访问；个人阅读状态与订阅配置保存在 `workspace_entries` 表。
- RSS：声明 `rss-parser` 依赖，接入时使用解析库，不复制旧原型的正则解析。
- 桌面：Electron，复用旧原型的窗口尺寸和本地服务思路；生产模式直接运行构建资源，服务随桌面生命周期关闭。
- 研究：后续封装单一研究适配接口，Node 后台执行，状态入库，前端轮询。具体工具认证与内容提取在接入时核实；骨架不假定工具已可用。
- 包管理器：npm，独立锁文件；Node.js 24。无相邻项目依赖。
- 浏览器开发数据：`data/local/`；桌面数据：操作系统应用数据目录，当前应用名 `Signal Desk Skeleton`，避免与旧原型混用。
- 上级已有原型不迁移、不覆盖；本次在指定子目录的骨架上推进组件化前端。最终替换旧版或迁移旧数据需单独明确范围。

## 后续实现顺序

1. 建立信源、文章、事件和个人记录的数据结构与迁移，明确稳定 ID 和增量获取语义。
2. 实现 RSS 配置与手动获取，覆盖部分失败、缓存与重复内容。
3. 完成三栏界面、收藏、笔记和原文回溯。
4. 接通研究工具、后台任务持久化和结果入库，验证失败与中断恢复。
5. 按 PRD 验收真实链路，再补独立安装包与发布验证。

## 完成标准

骨架：依赖可安装，语法及构建通过，开发/生产服务可启动，SQLite 重开后可读取，Electron 页面显示服务就绪。

MVP：核心流程使用真实数据贯通；重复获取不制造重复事件；收藏和判断重启后保留；失败不显示虚假成功。后续正式安装版应能脱离源码启动。

## 本轮前端交付（2026-09-08）

用户提供 14 份高保真 HTML 与设计规范，要求优先实现每日早报和正在关注。沿用 Vite 与 Electron 服务入口，引入 React 组件和 History 路由；Next.js 为用户举例，本轮不替换本地服务。详细路由、组件、数据边界和验收见 `docs/frontend.md`。

个人笔记、收藏、已读、访问足迹、专题关注与信源配置已本地持久化。RSS 连通性、文章抓取、模型交叉验证、真正日报生成仍属于后续工作。原型中的成功提示不得被视为真实网络任务已接通。
